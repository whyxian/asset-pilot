# 事故报告：概览接口超时导致前端加载失败

> 报告时间：2026-06-19
> 事故等级：P1（核心页面功能受损）
> 影响范围：概览页（`/api/v1/overview`）
> 状态：已修复

---

## 一、现象

用户在概览页的实际体验：

1. 页面一直 loading，十几秒不出数据
2. 前端 axios 15s 超时，自动重试，再等十几秒
3. 重试仍超时，前端最终显示「加载错误」
4. 用户手动刷新才恢复正常

后端日志佐证：

```
13:04:00 [ERROR] 获取汇率失败:
13:04:00 [INFO]  [GET] /api/v1/overview 200 21429ms   ← 单次请求 21 秒
13:04:09 [ERROR] 获取汇率失败:
13:04:09 [INFO]  [GET] /api/v1/overview 200 21011ms   ← 重试又 21 秒
13:04:25 [ERROR] 获取汇率失败:
13:04:25 [INFO]  [GET] /api/v1/overview 200 21144ms   ← 第三次仍 21 秒
```

三次请求各 21 秒，全部因前端 15s 超时被判失败，用户看到的就是「一直加载 → 报错」。

---

## 二、根因

不是一个 bug，是**三个问题叠加**，任意一个单独都不至于崩，叠加后把一个本该 <1s 的接口拖到 21s。

### 根因 1：汇率接口超时设成 20 秒（直接元凶）

`backend/app/utils/exchange_rate.py`，网络拉取汇率时：

```python
async with httpx.AsyncClient(timeout=20) as client:   # ❌ 20 秒
    resp = await client.get(_RATES_URL)
```

汇率数据源是 GitHub raw 上的一个 `mini.json`（几 KB）。这个文件：

- **正常情况**：几百毫秒返回
- **连不上时**（GitHub 在国内偶发不稳定）：连接 hang 住

设 20 秒超时意味着——只要连不上，请求就**卡满 20 秒**才失败。一个几 KB 的 JSON 文件，没有任何理由等 20 秒。这是把「最坏情况兜底」和「正常超时」混为一谈的错误。

**为什么是 20 秒这么离谱**：最初写的时候图省事，沿用了 httpx 默认偏宽松的值，没有针对「这个数据有多大、用户能等多久」做判断。属于典型的「超时时间拍脑袋定的，没经过设计」。

### 根因 2：行情与汇率串行执行（放大效应）

`backend/app/services/overview_service.py`，`get_overview` 里：

```python
quote_map = await self._quote_svc.fetch_quote_map_concurrent(...)  # 行情，最多 12s
rate_snapshot = await fetch_rates()                                # 汇率，最多 20s
```

行情拉取和汇率拉取**互不依赖**，却用 `await` 串行执行。最坏耗时是两者之和：12 + 20 = 32 秒。

即便行情很快（几秒），汇率卡 20 秒，整体也要 20+ 秒。串行让汇率这一个慢点拖垮了整个接口。

### 根因 3：汇率拉取无单飞（雪崩效应）

`fetch_rates` 没有去重机制。N 个并发请求同时触发时，每个都各自发一个网络请求：

```
概览 60s 轮询请求 A → fetch_rates → 网络请求（卡 20s）
前端超时重试请求 B → fetch_rates → 网络请求（卡 20s）   ← 又发一个
用户手动刷新请求 C → fetch_rates → 网络请求（卡 20s）   ← 又发一个
```

3 个请求 = 3 个卡 20 秒的网络请求叠加。GitHub raw 被并发轰击，反而更容易超时。这就是日志里连续三次 21 秒的原因——不是同一个请求慢了三次，是三个请求各自慢。

---

## 三、为什么会发生（设计缺陷）

不是单点失误，是**缺少「超时分级 + 资源隔离」的系统性设计**。具体三条：

### 缺陷 A：超时时间没有按「数据特性 + 用户体验」分级

项目里所有外部请求的超时是各拍各的，没有统一原则：

| 请求 | 数据 | 原超时 | 问题 |
|------|------|--------|------|
| 汇率 JSON | 几 KB | 20s | 远超用户耐心，且无「兜底已充足」意识 |
| 腾讯行情 | 几 KB | 10s | 偏长但可接受 |
| 天天基金 | 几十 KB | 15s | 偏长 |
| CoinGlass | 几 KB | 10s | 偏长 |
| Playwright 美股 | 渲染页面 | 20s | 合理（浏览器渲染本就慢） |

没有一条规则约束「外部小数据请求该等多久」。汇率这种几 KB 的文件，5 秒都算宽容。

### 缺陷 B：没有「兜底优先于等待」的意识

汇率已经有五级兜底（内存 → 磁盘 → 种子 → 硬编码），**根本不需要等网络成功**。但超时设 20 秒，等于在说「我宁可让用户等 20 秒也要拿到最新汇率」——这与兜底设计自相矛盾。有兜底就应该敢设短超时，失败立刻回退。

### 缺陷 C：缺少并发请求的资源隔离

`fetch_rates` 是个会被高频并发调用的函数（每个概览请求都调），但没有单飞（single-flight）机制。共享的外部资源（GitHub raw）被无节制并发轰击，慢请求互相叠加。任何「会被并发调用且依赖外部慢资源」的函数都该考虑单飞。

## 四、解决方案（已实施，commit `aa70aa7`）

### 修复 1：汇率超时 20s → 5s

```python
_FETCH_TIMEOUT = 5   # 五级兜底充足，不必久等，失败立刻走兜底
async with httpx.AsyncClient(timeout=_FETCH_TIMEOUT) as client:
```

5 秒对一个几 KB 的 JSON 已经非常宽容。连不上就 5 秒后走兜底，用户几乎无感。

### 修复 2：行情与汇率并发拉取

```python
quote_map_task = asyncio.create_task(
    self._quote_svc.fetch_quote_map_concurrent(groups, force_refresh=force_refresh)
)
rate_snapshot_task = asyncio.create_task(fetch_rates())
quote_map, rate_snapshot = await asyncio.gather(quote_map_task, rate_snapshot_task)
```

两者并发，最坏耗时从「行情 + 汇率」降到 `max(行情, 汇率)`。

### 修复 3：汇率拉取单飞

```python
_inflight: asyncio.Task | None = None

async def fetch_rates() -> RatesSnapshot:
    ...  # 缓存命中直接返回
    global _inflight
    if _inflight is None or _inflight.done():
        _inflight = asyncio.create_task(_fetch_rates_uncached())
    return await _inflight   # N 个并发请求复用同一个 task
```

N 个并发请求只发 1 个网络请求，其余等同一个结果。端到端验证：5 个并发请求，网络只调用 1 次，2 秒（慢请求时长）全部返回，而非 10 秒。

### 效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 汇率连不上时单次耗时 | 20s | 5s（走兜底） |
| 行情+汇率最坏耗时 | 12+20=32s | max(12,5)=12s |
| 3 个并发请求叠加 | 3×20s 各自卡 | 1 个网络请求，其余复用 |
| 是否触发前端 15s 超时 | 是（21s > 15s） | 否（< 15s） |

## 五、日后预防

### 预防 1：建立超时分级原则（写入编码规范）

外部请求超时按数据特性 + 兜底情况设定，不再拍脑袋：

| 类型 | 原则 | 参考值 |
|------|------|--------|
| 小 JSON / API（有兜底） | 兜底充足就敢设短 | 3-5s |
| 小 JSON / API（无兜底） | 按用户耐心 | 5-8s |
| 行情批量（多数据源并发） | 整体熔断阈值，小于前端超时 | 10-12s |
| 浏览器渲染（Playwright） | 渲染本就慢 | 15-20s |

**铁律：任何外部请求超时不得大于前端超时（当前 15s），否则后端慢点必导致前端超时。** 汇率 20s 违反了这条。

### 预防 2：兜底与超时必须配套

**有兜底就设短超时**。如果一个外部资源失败时有内存/磁盘/种子兜底，超时应激进（几秒），让失败快速回退。反之没兜底的才保守。本次汇率 20s 超时 + 五级兜底是自相矛盾的组合。

### 预防 3：并发热点函数必须考虑单飞

会被高频并发调用、且依赖外部慢资源的函数，默认要加单飞。判断标准：「这个函数会不会被 N 个请求同时调，且每次都打同一个外部资源？」是 → 单飞。`fetch_rates` 符合，之前漏了。

### 预防 4：独立资源并发化

service 层有多个互不依赖的外部调用时，默认用 `asyncio.gather` 并发，不要串行 `await`。审查清单：每次新增 `await 外部调用` 时，检查它能否和前一个并发。本次行情/汇率串行就是漏审。

### 预防 5：端到端超时链校验

建立「前端超时 > 后端最坏耗时」的不变量，并在 code review 时检查：

```
前端 axios 15s  >  后端单接口最坏耗时（含所有外部调用 + 兜底）
```

后端最坏耗时 = 所有串行外部调用的超时之和（并发则取最大）。本次 32s 远超 15s，review 时本应发现。

## 六、遗留与后续

- 本次只修了汇率。**行情数据源（腾讯/天天基金/CoinGlass）的超时仍偏长（10-15s）**，且有 12s 整体熔断兜底，暂不紧急，但应按预防 1 的原则重新评估。
- 前端 axios 15s 超时是否合适，也值得重新审视——概览这种轻量接口，8-10s 超时可能更符合用户预期。
- 建议把「超时分级原则」补进 [CLAUDE.md](../../CLAUDE.md) 编码规范，作为日后硬约束。

---

## 七、复盘结论

**这不是一个「汇率接口慢」的问题，是「超时设计缺失」的系统性问题在汇率这个点上爆发。** 20 秒超时是拍脑袋定的，没有考虑数据大小、用户耐心、兜底情况；串行执行和缺少单飞是配套的资源管理缺失。三个问题单独都能容忍，叠加后把一个几 KB JSON 的拉取放大成 21 秒的接口灾难。

修复不止是改个数字，而是补上「超时分级 + 兜底配套 + 单飞 + 并发化」这套本该有的设计。日后靠预防 1-5 的规则约束，避免同类问题在别的接口复发。
