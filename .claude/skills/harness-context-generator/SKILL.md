# Harness 工程文档生成器

为项目生成/更新一套 AI 上下文文档。**适用场景：新项目脚手架或已有项目需新增上下文文档。**

## 产物位置（按"是否需工具加载"分类）

1. **生效文件 → 标准位置**（工具自动加载，放别处不生效）：
   - `CLAUDE.md` / `AGENTS.md` → **项目根目录**
   - 规则文件 → **`.claude/rules/`**
   - 写入前确认：目标已存在时走增量合并（user/lock 保护区，见 §3），**不静默覆盖**
2. **规范文档**（ARCHITECTURE/TESTING/DATABASE 等参考类）→ **`docs/harness/`（默认）**
   - 与项目现有 `docs/` 体系隔离，文件名通用不冲突
   - **索引时机与文件位置解耦**：无论落点如何，生成时立即进根文档索引（防孤儿，见 §2.2 覆盖度检查）；并入 `docs/` 仅文件移动 + 索引路径同步，须用户明确要求
3. **skill 内部状态** → `.harness/state.json`、`.harness/backups/`（备份集中管理，不散落项目各处）

## 核心原则

1. **先分析，后操作**：基于真实代码/配置/依赖，不臆测；不确定处标 `[待确认]`，禁止编造
2. **按需加载**：根文档（AGENTS.md/CLAUDE.md）保持精炼做索引，细节进 `docs/harness/`
3. **可执行**：产出的命令、路径必须能在项目里直接运行
4. **保护用户内容**：`<!-- user:start/end -->` 内为可保留区，更新时原样带回；`<!-- user:lock:start/end -->` 内为锁定区，任何模式不得改动其内容
5. **索引真实**：根文档的文档索引只列实际生成的文档，不预置空条目
6. **引导必带推荐**：所有向用户提问的交互（产物选择/落点/并入/文档提议/回滚等）必须给出**推荐选项**（标注"✅ 推荐"）——推荐 = 基于当前检测的最优解，并说明理由；用户可一键采纳、改选其他或否决。禁止抛出无倾向的开放式选择

## §0 初始确认：产物与场景

先问用户（不要假设），但**必带推荐**：
- **产物与决策提示**：
  - 只用 Claude Code → 生成 **CLAUDE.md**（Anthropic 原生，会话自动加载）
  - 多个 AI 工具协作（Codex/Cursor/Jules…）→ 生成 **AGENTS.md**（跨工具通用标准，Claude Code 也读它）承载团队通用约定，可选再生成 CLAUDE.md 承载 Claude 特有能力细节
  - 两者并存时：通用内容放 AGENTS.md，Claude 专属（hooks/技能等）放 CLAUDE.md
  - `.claude/rules` 与 CLAUDE.md 配套才生成
  - 推荐逻辑：检测到多工具配置文件/用户提及多工具 → **✅ 推荐两者都生成**（AGENTS 通用 + CLAUDE 补充层）；仅 Claude 单工具使用 → ✅ 推荐仅 CLAUDE.md
- **落点**：按"产物位置"三分类执行——生效文件写标准位置（已存在则走更新合并），规范文档默认 `docs/harness/`
- **场景**：存量项目已有 `docs/` 体系 → 规范文档默认 `docs/harness/` 隔离不冲突（并入见"产物位置"）
- **协作模式（决定状态基线是否入库）**：团队多人都会跑本 skill 更新文档 → **✅ 推荐共享 state.json 基线**（`.gitignore` 放行 `state.json`，clone 即得基线、防多人各自校准漂移；`.backups/` 保持本地）；仅个人维护 → ✅ 推荐全本地（`.harness/` 全忽略，现状）。按选择配置 `.gitignore`

## 操作模式

| 触发 | 模式 | 行为 |
|------|------|------|
| `--full`（或首次） | 全量生成 | 按 §2 生成：根文档/规则写标准位置，规范文档写 `docs/harness/`，状态写 `.harness/` |
| `--root-only` | 仅根文档 | 只生成/更新根文档（跳过 docs 与 rules） |
| `--doc <主题>` | 按需单文档 | 用户指定主题 → 定位相关代码 → 归纳生成单份文档（见 §2.5） |
| `--update` | 增量更新 | 对比签名 → 报告 → 备份 → 更新 |
| `--check` | 仅检测 | 对比签名出报告，不写任何文件 |
| `--rollback` | 回滚 | 从 `.bak` 备份恢复 |

## 阶段 1：项目分析（所有模式必做）

1. **技术栈**：依赖清单（`pyproject.toml` / `requirements.txt` / `package.json` / `go.mod`…）→ 框架、ORM、测试工具
2. **结构**：根目录主要目录及用途、源码目录、配置文件位置（`.env.example`、`tsconfig.json` 等）
3. **命令**：安装 / 启动 / 测试 / lint / build 的可执行命令
4. **现有资产**：README、现有 CLAUDE.md/AGENTS.md、`docs/` 内容、git 约定
5. **Monorepo**：有 `packages/` 等多子包时询问"每子包独立文档 + 根索引"或"仅根一份"
6. **数据库**：优先读 schema 文件 / 连接串前缀精确确认（如 `prisma/schema.prisma` 的 provider、`DATABASE_URL` 前缀）；禁止仅凭依赖包名下结论
7. **CI/部署**：Dockerfile、`.github/workflows/` 等是否存在（决定是否生成部署类文档）

分析后**先向用户简述发现与计划，确认后再写入**。

## 阶段 2：全量生成（--full）

### 2.1 根文档（项目根 / CLAUDE.md 或 AGENTS.md）

**目标文件不存在** → 按模板结构生成。

**目标文件已存在（存量项目常态，多半无保护区标记）→ 理解后合并优化**。用户调用本 skill 即包含"希望优化已有 CLAUDE.md"的意图，优化三原则：**语义保真**（原有有效约束/红线/信息点不丢）、**精简**（CLAUDE.md 是上下文入口，宜精简不宜膨胀）、**不影响原有使用**（优化后覆盖原有全部能力）。

1. **先完整阅读**现有文件：结构、章节、文风、已含的红线与约束，识别哪些是用户精心维护的语义资产
2. **差异分析**：与 §1 实际分析对比——缺哪些章节 / 哪些命令已过时 / 哪些信息重复或冗长可合并
3. **合并重构**：在语义保真前提下主动优化——去重、精简冗述、结构重组（相似内容归并章节）、补齐缺口；删改任何已有内容前，逐项向用户展示"改什么、为什么、原有语义是否保留"，经确认后执行
4. 本 skill 自身生成过的文件（含 user/lock 保护区标记）按 §3 合并规则走；保护区内的内容原样保留

### 2.2 规范文档（默认 docs/harness/ 下，按检测结果生成，不预置全集）

**落点先询问**：生成前检测项目 docs/ 现状——
- `docs/` 不存在或为空（全新项目）→ **主动问用户**（带推荐）："本项目没有现有文档体系——✅ **推荐直接生成到 `docs/`**（无冲突风险、位置更自然）；或 `docs/harness/`（隔离）？"
- `docs/` 已有成熟体系（存量项目）→ ✅ 推荐默认 `docs/harness/` 隔离（见"产物位置"），不询问

**生成前先做覆盖度检查**（实测教训）：对比项目现有 docs/ 与根文档已含的约定——内容已被覆盖的**不生成**（引用现有即可），宁可少生成不可生成孤儿文档；**不被根文档引用 = AI 不会读 = 无价值**，生成的每份规范文档**生成时立即**加进根文档索引（不等并入 docs/）。覆盖度检查对强触发同样生效（见下）。

每个文档：标题 + 更新说明 + `user:start/end` 保护区 + 真实要点（从代码/配置提取）。文件名用通用规范名（如 ARCHITECTURE.md/TESTING.md），与项目现有 docs 重名也无冲突（目录隔离；并入 docs/ 见"产物位置"）。

**触发分层（2026-09-03 用户确认）：强触发直接生成，弱触发仅提议**

**强触发**（检测到对应物 → **直接生成，不再询问**；仍受覆盖度检查约束）：

| 检测到 | 生成 | 内容来源 |
|--------|------|---------|
| 有源码结构/模块分层 | `ARCHITECTURE.md` | 模块职责与依赖 |
| 有数据库（schema/ORM/迁移） | `DATABASE.md` | 表结构/约束/操作红线 |
| 有测试文件 | `TESTING.md` | 测试模式、运行命令、陷阱 |
| 有显著 API 层（路由/端点） | `API_GUIDELINES.md` | 返回格式/错误码/端点分组 |

**弱触发**（检测到 → **向用户提议**，确认后生成或并入根文档）：

| 检测到 | 提议生成 |
|--------|---------|
| 有 CI/部署配置 | 部署文档（Dockerfile/工作流） |
| 有特别规范约束（编码风格配置显著自定义等） | 对应规范文档 |
| 业务领域资产 / 复杂运行环境 | 见 §2.2.1（业务命名 + 推荐引导） |

### 2.2.1 业务领域专项文档（AI 自主检测）

通用检测表覆盖不了**业务领域资产**（核心算法/领域模型/业务规则）——它们往往藏在纯函数模块、Service 层或领域代码里，被通用文档漏掉。**AI 必须主动识别并向用户提议**（不自动生成，先确认）：

| 检测到的情况 | 触发示例 |
|-------------|---------|
| 核心业务算法 / 财务公式 / 计算逻辑（纯函数模块） | 投资看板：做T ROI / XIRR / Modified Dietz |
| 复杂 Service 层 / 领域模型（状态机、领域规则） | 交易→持仓回放反推、清仓归档链路 |
| 事件驱动 / 消息队列 / 定时任务体系 | 调度器预热、失败兜底链路 |
| 缓存 / 多租户 / 数据迁移等专项架构 | — |
| 前端组件库 / 设计系统 | — |
| **复杂运行环境**：`.env.example` 变量多（>8 且含义不自明）/ 外部依赖服务（Redis、独立 DB、docker-compose 编排）/ 启动前需数据准备步骤 | 提议生成运行文档（每个变量含义、依赖启动顺序、数据准备步骤；命名如 `PROJECT_SETUP.md` 或业务命名） |

**执行规则**：
1. 检测到显著业务域 → **向用户提议**（带推荐：✅ 推荐生成——提议已说明价值；选项 Y 生成 / n 跳过 / 并入已有文档），确认后生成
2. **文件名用业务术语**（非通用模板名）：从模块名/类名/README 提取；命名示例：`FINANCIAL_FORMULAS.md`、`TRADE_RECONCILIATION.md`；无法识别用 `CORE_DOMAIN.md` 兜底
3. 文档内容**从代码真实提取**（函数签名/公式/关键决策），不确定标 `[待确认]`
4. 落点与索引规则同 §2.2（生成即进根文档索引，防孤儿）
5. 收尾报告列出"提议过/生成/跳过"的专项文档

### 2.3 规则文件（.claude/rules/，仅产物含 CLAUDE.md 或用户要求时）

规则文件的核心价值是让 Claude Code 自动加载根文档。如果不使用 Claude Code，规则文件无实际作用。

`must-read-context.md` 写入 `.claude/rules/`（工具自动加载位置；已存在同名文件时走合并确认），**frontmatter 必须含 description**（Claude Code 靠它索引规则）：

```markdown
---
description: 执行代码任务前必须先读根上下文文档
paths:
  - "*"
---

# 先读上下文

执行任何代码分析/修改前，必须先读根目录的 CLAUDE.md（或 AGENTS.md）。

例外：与代码无关的通用问答。
```

### 2.4 状态文件（.harness/state.json）

```json
{
  "version": "1.0.0",
  "generatedAt": "生成时间",
  "gitHead": "生成时点的 HEAD commit（git rev-parse HEAD）",
  "files": { "相对路径": "内容摘要" }
}
```

- 摘要：**真实计算**——用 Bash 跑 `sha256sum <文件>`；对目录结构用 `find <dir> -type f | sort` 的输出 hash
- ⚠️ **目录 hash 实测教训**：`find` 的排除模式（如 `-path "*__pycache__*"`）在 shell 字符串里会被通配符展开破坏参数——用引号包裹，或直接用无 shell 的列表参数方式执行（Python subprocess 不带 shell=True）；生成后应**自证一次**（重算对比 state.json）
- **`gitHead` 仅作审计参考**（文档对应哪个代码版本）；变更检测**始终以内容 hash 为准**——commit id 会漏报（未提交的本地修改）与误报（无关提交），不得作为检测依据
- 监控对象：根文档 + 各规范文档的来源文件（依赖清单、schema、目录结构、CI 配置），与 §3 变更检测表对应

### 2.5 按需单文档（--doc <主题>）

用户直接指定主题（如"行情数据源"、"交易重算逻辑"）时，不走全量检测——针对该主题做归纳生成：

1. **主题澄清（必须先做）**：用户主题常简单或有歧义——**通过对话确认范围**再动手。向用户展示你对该主题的理解与可能的文档方向（**标注 ✅ 推荐方向**：按主题词与代码匹配度给出最可能的一个，如用户说"行情"且数据源层最显著 → ✅ 推荐"行情数据源"），让其选择/修正；展示将覆盖哪些模块与信息源后开始
2. **定位相关代码**：扫描与已确认主题相关的模块/配置/调用方（如"行情数据源"→ `core/data_sources.py` + 各 repo + 调度器调用点），确保文档反映全貌而非单文件
3. **覆盖度检查**：docs/ 或 docs/harness/ 已有同主题文档 → 提示"已有 X，建议更新还是新建独立文档"，不静默重复生成
4. **真实提取**：内容从代码/配置提取，不确定标 `[待确认]`；若主题超出代码可归纳范围（如公司流程），如实说明并留占位
5. **命名**：优先用用户指定名；未指定则按业务术语（如"行情数据源"→ `QUOTE_DATA_SOURCES.md`）；落点与索引规则同 §2.2
6. 生成后收尾报告说明：覆盖的模块、提取的信息源、[待确认] 项

## 阶段 3：增量更新 / 检测（--update / --check）

1. 读 `.harness/state.json`；缺失时提示先 `--full` 或按"全部视为新增"继续（需确认）
2. 重新计算各监控对象摘要 → 差异 → 生成报告：
   - 已有文档影响面：需更新 / 无需更新
   - **新领域检测**：结构/领域新增承载显著新业务域（新模块/新能力，如新增"定投计划"模块）→ **向用户提议为其生成独立专项文档**（同 §2.2.1 流程：说明理由 + 建议命名 → 确认后生成），而非只并入已有文档
3. `--check` 到此为止，**根据报告引导用户下一步**：基线缺失或新增领域多 → 建议 `--full`；变更小且可控 → 问是否执行 `--update`；无变更 → 说明无需操作
4. `--update` 执行（每份文档）：

```
备份: 被更新文件（标准位置或 docs/harness/ 内）→ .harness/backups/<文件名>.bak.<日期>
提取: 现有文档的 user/lock 保护区内容
重生成自动部分（基于当前项目真实状态）
合并（见下）→ 写回 → 变更处附近标 🔄
```

5. 缺失文档：根文档/rules（工作流入口，标准位置）缺失直接重建并告知；`docs/harness/` 内规范文档缺失询问（全部重建 / 逐个 / 跳过）。若 `.bak` 中存在用户保护区内容而现文档丢失，提示可恢复。

### 合并规则

- **优先级**：锁定区 > 用户区 > 自动内容；存量未标记内容按 §2.1 的"语义保真 + 精简"原则合并处理
- 锁定区：内容绝不动；所在章节被删时，整个锁定块移到文档末尾保护区，报告中说明
- 用户区：按**章节标题**映射到新文档同标题位置；标题不存在则保持原相对顺序位置；兜底放文档末尾保护区
- 同标题冲突：保留用户内容、自动内容让位，报告标记冲突位置
- **存量内容合并**：有效语义（约束/红线/信息点）全部保留，表达上允许去重精简归并；任何删改先展示计划并确认（见 §2.1 步骤 3）
- 保护区外的用户手改（更新会被覆盖）：报告中提醒迁入保护区

## 阶段 4：回滚（--rollback）

1. 扫描 `.harness/backups/` 下 `*.bak.<日期>`，按文档分组列出（含日期）
2. 用户选（带推荐）：**A 全部恢复最新（✅ 推荐**——回滚通常因最近一次 update 不满意）/ B 逐个选版本 / C 取消
3. 恢复前当前文件先存 `原文件.bak.rollback.<日期>`（同在 .backups/）
4. 完成后建议执行 `--check` 校验状态

## 阶段 5：收尾报告（所有写操作模式）

1. 摘要：创建/更新/跳过清单 + 原因，**按三类分组列出**：标准位置（根文档/规则）/ `docs/harness/`（规范文档）/ 内部状态
2. 保护区内容保留确认；待用户手动补充的点（公司规范等）
3. 规范文档已默认落 `docs/harness/` 且**生成时已被根文档索引**；存量项目收尾**主动问一次并入**（带推荐）："这 N 份规范要并入 `docs/` 吗？"——✅ **推荐按主题去重后并入**（docs/ 已有同主题文档 → 推荐保留隔离避免重复；无同主题 → 推荐并入 docs/ 更自然）；逐份确认 + 同步导航后由本 skill 移动文件与索引路径
4. 建议验证：让用户跑一条生成文档中的命令，确认可执行

## 约束

- 不要臆造内容；命令必须真实可运行；所有写操作前有用户确认
- **写位置按分类执行**：根文档/规则只写标准位置（已存在走合并，不静默覆盖）；规范文档默认只写 `docs/harness/`，并入 `docs/` 需逐份确认
- 存量项目有成熟 docs 时不得整目录重建；先 `--check` 沟通
- 文档语言跟随项目现状（README/注释语言），不强制英文或中文
- `.harness/` 是本地工具状态（含备份），默认纳入 `.gitignore` 不入库；团队如需共享文档变更基线，可选择性放行 `state.json`（gitignore 例外）
